# Run L4-Prime Loop

> `using-epi-logos` runs first. If it hasn't been invoked this turn, go there now.

`L4'` is the scientific verification loop within Square B — the Cause-Experience basin. It gives the objective run-shape for moving from current state to ideal state through verifiable iteration. It is the essay's L4′-prime verification lens made operational — the check `/mef-refract` runs when a lens's finding claims to be tested rather than merely asserted.

Square B companions are always co-present: L1 (what causal structure is being tested), L4 (how the verification process is lived and disclosed — what matters, what is at stake), and L1' (which phenomenal functions orient the evaluation — what is felt before it is measured). The loop runs inside this basin, not in isolation.

The loop: **Observe → Think → Plan → Build → Execute → Verify**, with outer **Learn**.

Build before Execute. This is not negotiable. If you execute without building the evaluative apparatus first, there is nothing honest to verify against — the loop is just motion.

## The Loop

The six stages are the six positions of a P0→P5 traversal read through L4'; the position tag names what each stage *is*, not a file to write. (If a run has a persistence surface, each stage's product files there; the minimal plugin ships no such scaffold, so treat the tags as structure, not paths.)

**Observe** *(P0 / Truth)* — Gather actual context. Current state, user intent, constraints, available evidence, what remains unknown.

**Think** *(P1 / Mind)* — Generate candidate explanations and target states. What are plausible interpretations? What is the desired state? What explains the gap?

**Plan** *(P2 / Word)* — Design the method. Ordered steps, blockers and risks, why this path rather than another.

**Build** *(P3 / Logos)* — Build the evaluative apparatus before acting — success criteria, validation rules, what pass and fail look like. This is where verification becomes possible rather than theatrical.

**Execute** *(P4 / Son)* — Perform the intervention — code changes, research actions, tool runs, structured analysis, writing with operational consequence.

**Verify** *(P5 / Image)* — Measure the outcome against the criteria established in Build. Pass, fail, or partial pass requiring recursion. If verification fails, recurse honestly rather than decorating failure as insight.

**Learn** *(the outer X, L4''s macro-environment)* — Carry forward only what survived verification. What is now durable? What method improved? What changes in the next cycle? Successful verification feeds upward into Learn, which conditions the next run.

## Rules

- Build before Execute. Always.
- Keep paradigm-awareness: evidence and success are never fully frame-neutral.
- Check Square B companions periodically: Is L1 (causal structure) aligned with what you are testing? Is L4 (lived disclosure) registering something the loop is missing? Is L1' (felt evaluation) flagging a qualitative shift the metrics cannot capture?
- If the objective loop is moving but the larger field is still incoherent, hand off to `investigate` (the eight-fold interrogative walk).
- When the loop surfaces a disclosure/causation gap (what you're building vs what it claims to do), hand the diagonal to `apply-cmea`.
- When the full basin needs mapping rather than just the verification loop, hand to `engage-encounter-axis`.

## Output

Natural chat reporting the run — current state, the criteria built, the outcome measured against them, and what survived into Learn. Close with a small mark (e.g. `⟨Square B · L4' — Verified⟩` or `⟨… — partial, recursing⟩`). Never decorate a failed verification as insight; say it failed and recurse.
