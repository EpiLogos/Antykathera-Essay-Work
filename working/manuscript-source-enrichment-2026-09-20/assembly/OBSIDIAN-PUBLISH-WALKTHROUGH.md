# Obsidian Publish walkthrough — publication design

Date: 2026-09-23
Standing: implementation design for the accepted/public reading projection; not authority over the manuscript
Repository branch: `codex/manuscript-source-enrichment-2026-09-20`

## Purpose

Use Obsidian Publish as the public, read-oriented walkthrough for *The Return of Zero* and its selected surrounding field. This replaces neither the sovereign manuscript nor the full private vault. It is a **generated public projection**: enough structure for a reader to move from the essay into arguments, concepts, Mythemes, Mathemes, products and sources without exposing private working material.

The design should preserve the essay's linear reading while making the non-linear field available around it.

## Why Publish fits

Current Obsidian Publish provides the parts this project actually needs for a first public field:

- configurable homepage and navigation;
- internal links, hover previews and backlinks;
- search;
- table of contents;
- a published graph view;
- stacked pages/sliding-window reading;
- custom CSS;
- custom domain support;
- page-level permalinks and metadata;
- headless/CLI publishing for Git-based workflows.

The published graph is deliberately secondary. Publish's graph is materially simpler than the desktop application's graph and does not provide the full filtering/sorting system we originally wanted. Therefore **the walkthrough must be authored in links, maps and navigation, with the graph as an ambient field rather than the only wayfinding mechanism**.

Community-plugin-dependent views such as live Dataview should not be part of the public contract. Where a useful index is presently generated by plugin logic, materialise it to ordinary Markdown during the projection build.

## Publication boundary

Do **not** point Publish at the repository root and publish opportunistically.

Build a clean projection vault, proposed path:

```
working/publish-vault/
```

or another explicitly generated destination approved by the repository's publication protocol.

Only admitted public material enters this vault. In particular, exclude:

- raw chats and derivational transcripts;
- private authorial NOTES unless deliberately adopted;
- source-recovery ledgers and model review receipts;
- local-machine details and private project state;
- unapproved first-person testimony;
- rejected or superseded manuscripts;
- internal governance/workflow metadata not needed by a reader.

The projection is disposable and rebuildable. Its sources remain the accepted manuscript and admitted canonical/public field.

## Reader architecture

### 0. Home — **The Return of Zero**

A sparse entrance with four clear acts:

1. **Read the essay**
2. **Walk the argument**
3. **Enter the field**
4. **Follow a thread**

The home page should explain in two or three paragraphs that the essay can be read linearly, while the surrounding field preserves the sources, arguments, images and formal constructions through which it was made.

### 1. Essay

Publish the accepted essay in two coordinated forms:

- **Whole essay** — one long reading page.
- **Eight section pages** — §0/1, §0, §1, §2, §3, §4, §5, §5→0.

Section pages should link Previous / Whole essay / Next and expose their six movements through the page outline.

The whole page remains canonical for continuous reading. Section pages are generated views of the same accepted text, not independent manuscripts.

### 2. Walkthrough

Nine short authored guides:

- 00 — What is it that knows?
- 01 — Definition, limitation and the Subject
- 02 — Differentiating Mind and Objective Internality
- 03 — The Return of Zero
- 04 — Dia, Syn, Trust and the Other
- 05 — The formal body: 4+2, Spanda and return
- 06 — Psychoid flowering
- 07 — Objective Internality as technological field
- 08 — Epi-Logos, Technē and release

Each guide should be a real path, not a summary of the corresponding section. It selects a handful of canonical nodes and says what changes as the reader crosses them. A reader should be able to continue linearly or branch into the field at any step.

### 3. Field

Public collections:

- **Arguments** — admitted A records used by the essay.
- **Concepts** — selected C records required to understand the essay.
- **Mythemes** — whole narratives/images, not extracted motif cards.
- **Mathemes** — worked formal constructions and diagrams.
- **Products / O:I** — one O:I field and its six technological facets.
- **Sources** — public source records and reading provenance suitable for publication.

Do not dump every canonical object. Start from nodes actually consumed by the accepted manuscript and expand deliberately.

### 4. Threads

Curated Maps of Content that cut across sections:

- Subject / Definition / Formal Limit
- Zero / One / Two Ones
- Recognition / Instrument / Return
- Dia / Syn / Trust / Power
- Name / Power / Labour / Economy
- Mytheme → Matheme
- Psychoid / Arche-Topos / Objective Internality
- AI agency / pramātṛ–pramāṇa–prameya
- Technē / Commons / Compassion
- Antikythera / instrument / attunement

These are the principal replacement for the sophisticated filtered graph the desktop application has not yet delivered.

## Graph and visual behaviour

Enable Publish's graph, but style it as a quiet field rather than the primary navigation.

Use stable public tags/classes on generated notes, for example:

- `field/argument`
- `field/concept`
- `field/mytheme`
- `field/matheme`
- `field/product`
- `field/source`
- `essay/section`
- `walkthrough`

Keep the graph sparse by publishing only admitted nodes. Where a particular formal or symbolic constellation requires exact geometry, publish a generated static SVG/PNG or ordinary Markdown diagram alongside the note; do not depend on the Publish graph to reproduce Bimba/QL geometry.

## Navigation

Suggested public order:

1. Start Here
2. Essay
3. Walkthrough
4. Threads
5. Field
6. Sources
7. About / Method

Hide generated support notes from navigation where they are useful only through links.

Enable:

- navigation;
- search;
- table of contents;
- backlinks;
- hover previews;
- theme toggle;
- stacked/sliding pages.

The stacked-page behaviour is especially close to the intended walkthrough experience: a reader can open linked objects without losing the path they were following.

## Page metadata

Every generated public note should carry:

```yaml
---
publish: true
permalink: ...
description: ...
aliases: [...]
---
```

Use stable permalinks for the essay and primary field objects. Page descriptions should describe the note's actual operation, not marketing copy.

## Theme

Create a root `publish.css` derived from the approved editorial language of the essay reader:

- restrained wide margins;
- strong serif reading face using safe/web fonts;
- quiet small-caps or sans metadata;
- clear mathematical blocks;
- minimal borders;
- field/type cues that do not turn the site into a dashboard;
- responsive section navigation;
- visible but subordinate backlinks and graph.

Do not begin with custom JavaScript. Publish supports `publish.js` only with a custom domain; use it only if a later interaction cannot be achieved through native Publish behaviour and CSS.

## Media

Keep images small and optimised. Host large video externally and embed/link it. The public walkthrough should not depend on embedded PDFs on mobile; link source PDFs externally where appropriate and retain readable source notes in Markdown.

## Build route

Create one deterministic builder, e.g.

```
tools/build-obsidian-publish.py
```

Responsibilities:

1. read the accepted manuscript;
2. split its eight generated section views without changing prose;
3. copy admitted canonical field nodes;
4. rewrite repository-relative links into public vault wikilinks where needed;
5. generate MOCs / walkthrough navigation as ordinary Markdown;
6. attach publication frontmatter and stable permalinks;
7. copy approved media;
8. generate `publish.css`;
9. fail on broken internal links, duplicate permalinks, missing public targets, or forbidden/private path leakage.

The build should never edit the authoritative source files.

## Headless publication route

Obsidian's current headless Publish client can publish a vault from the command line. After the projection is built and the user has authenticated an Obsidian Publish account/site:

```bash
npm install -g obsidian-headless
ob login
ob publish-list-sites
cd <generated-publish-vault>
ob publish-setup --site "<site-slug>"
ob publish --dry-run
ob publish
```

Because headless Publish defaults to `publish: true`, the projection should use explicit publication flags rather than `--all` in normal operation.

Site options should expose navigation, graph, outline, search, backlinks, hover previews, theme toggle and sliding-window/stacked-page reading, with a deliberate navigation order and hidden support notes.

## Initial implementation wave

1. Fetch and locally verify the accepted whole-manuscript candidate.
2. Build the generated Publish vault with only:
   - Home;
   - whole essay;
   - eight section views;
   - nine walkthrough guides;
   - ten thread/MOC pages;
   - the smallest source/argument/concept/Mytheme/Matheme set needed for those guides.
3. Add native Publish navigation, graph, backlinks, search, hover previews and stacked pages.
4. Add the first `publish.css`.
5. Run a private/passworded Publish preview if desired.
6. Walk the site as a new reader; only then expand the public field.

## Acceptance criteria

The first Publish version succeeds when:

- the essay can be read continuously without entering the field;
- every walkthrough step has a clear next step and meaningful optional branches;
- field nodes reveal genuine provenance and relations rather than duplicated prose;
- the graph is informative but never required for navigation;
- no private/working source leaks into the published vault;
- mobile reading remains clean;
- a local source correction can rebuild and republish the affected public projection without hand-editing published copies.
